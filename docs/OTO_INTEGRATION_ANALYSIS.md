# OTO Integration Analysis: WaslShip Logistics Architecture

## 1. Project Overview
WaslShip is a logistics aggregator platform that leverages OTO as a core gateway to multiple shipping carriers. The system is designed to provide a unified shipping experience for multiple merchants through a single platform-level integration.

## 2. Core Requirements Analysis

### 2.1 Multitenancy & Data Isolation
The system must support multiple independent merchants within a single OTO master account.
- **Shared Account Logic**: WaslShip holds the primary API credentials.
- **Tenant Identification**: Every outbound order uses a unique `TrackingNumber` generated by WaslShip (e.g., `WS2026...`) as the OTO `orderId`.
- **Isolation Mapping**: The `ShipmentService` database maps `TrackingNumber` -> `MerchantId`. Webhooks arriving from OTO are routed back to the specific merchant using this mapping.

### 2.2 Virtual Wallet & Financial Reconciliation
A real-time ledger system to manage merchant funds and OTO charges.
- **Prepaid Flow**: Funds are deducted from the Virtual Wallet upon shipment confirmation.
- **Settlement Flow**: COD (Cash on Delivery) collections are credited back to the Virtual Wallet after OTO processes the carrier settlement.
- **Reconciliation**: Continuous monitoring of `walletTransaction` webhooks to ensure internal ledgers match OTO's financial reported state.

### 2.3 OTO Lifecycle Synchronization
Tracking the physical parcel journey and reflecting it in the platform.
- **Inbound Sync**: `orderStatus` webhooks update local `Shipment` states.
- **Outbound Sync**: Order creation, updates, and cancellations are pushed to OTO's REST API.
- **Error Handling**: `shipmentError` webhooks mark orders as `Failed` and notify merchants of actionable issues (e.g., address out of coverage).

### 2.4 Merchant Management (User Service)
Configuration and identity management for platform tenants.
- **Pickup Locations**: Merchants manage their own physical locations, which are mapped to OTO `pickupLocationCode`.
- **Merchant Profiles**: Storage of merchant-specific branding, notification preferences, and API access levels.

## 3. Technical Implementation Strategy

### 3.1 Security Model (HMAC-SHA256)
All webhooks must be verified using a shared secret key.
- **Logic**: `Base64(HMAC-SHA256(SecretKey, orderId:status:timestamp))`
- **Implementation**: Handled by the `OtoWebhookValidator` service.

### 3.2 Event-Driven Architecture
WaslShip uses an internal message bus (MassTransit/RabbitMQ) to decouple services.
- **Producer**: `ShipmentService` (on webhook receipt).
- **Consumer**: `WalletService` (for deductions/credits), `NotificationService` (for SMS/Email updates).

### 3.3 API Layer
Standardized REST endpoints for merchants to interact with their isolated data, proxying necessary calls to OTO while enforcing multitenancy constraints.
